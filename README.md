# Math Trace Validity

Checks whether Chain-of-Thought traces generated by
[Goedel-Prover](https://huggingface.co/Goedel-LM/Goedel-Prover-SFT) are valid
Lean 4 proofs. Steps come from
[FormalStep](https://huggingface.co/datasets/liuchengwu/FormalStep); generated
Lean 4 code is checked against a local Lean 4 REPL via
[lean_interact](https://github.com/lean-dojo/lean-interact).

Generation needs a GPU and no Lean. Verification needs Lean and no GPU. They are
separate commands on purpose, and traces are the interchange format.

## Project structure

```
trace_valid.py       # CLI: generate (GPU) | run (GPU+Lean) | analyze
config.py            # model, dataset, sample selection, Lean pins, token budget
data_loader.py       # FormalStepDataset + sample selection strategies
prompting.py         # Goedel prefix-completion prompt; Lean-block extraction
model.py             # GoedelProver: VRAM preflight, generation, truncation flags
generate.py          # trajectories -> JSONL + run_meta.json
verify_traces.py     # traces -> verification JSONL (outcome taxonomy)
verifier.py          # LeanVerifier: pinned project, shared Mathlib env, outcomes
analyze_runs.py      # per-run report, validity rate, cross-tab, paired compare
analysis.py          # older stats/plot helpers for `trace_valid.py run`
tests/               # verifier control set, dataset cross-check, pipeline trace
traces/              # one directory per run: traces.jsonl + run_meta.json
results/             # verification JSONL, analysis JSON, plots
```

## Setup

### 1. Python dependencies

```bash
pip install -r requirements.txt
```

Versions are pinned. Unpinned, `pip install transformers` resolves to 5.x on a
fresh GPU image and the model import dies with `Could not import module
'LlamaConfig'` before a single trajectory is generated. Do not fix a conflict
here by dropping a pin. `torch` is deliberately unpinned — its CUDA build must
match the host driver.

If a machine has previously used a newer `datasets`, clear
`~/.cache/huggingface/datasets` first: a cache written by datasets 5.x is
unreadable by the pinned 3.6.0 (`Feature type 'List' not found`).

### 2. Lean 4 and Mathlib

```bash
bash setup_lean.sh
```

Installs `elan` and the pinned toolchain, then builds the Lean project through
`verifier.setup_lean_project()`, which runs `lake exe cache get` **before**
`lake build`. Mathlib is downloaded, never compiled from source.

#### Version pinning — do not bump these independently

| Component | Pin | Where |
|---|---|---|
| Lean toolchain | `leanprover/lean4:v4.32.0` | `config.LEAN_VERSION`, `lean_project/lean-toolchain` |
| Mathlib | tag `v4.32.0` | `lean_project/lakefile.toml` (generated) |
| REPL | `augustepoiroux/repl` @ `v1.3.18` | resolved by `lean_interact` |

`lean_interact` picks its REPL by checking out `{repl_rev}_lean-toolchain-
{lean_version}`. That rev publishes 94 such tags, topping out at `v4.32.0` —
**there is no `v4.32.2` tag**, so a project on Mathlib v4.32.2 runs against a
mismatched REPL and produces `unexpected token` / `unknown constant`. mathlib4
tag `vX.Y.Z` always declares `leanprover/lean4:vX.Y.Z`, so naming the Mathlib tag
after the Lean version is what keeps all three aligned. The same argument rules
out `-rc` toolchains: they have no matching Mathlib or REPL tag.

### 3. Windows: add Defender exclusions before loading Mathlib

Mathlib is ~8,600 `.olean` files. With Defender real-time protection scanning
each read, loading measured **7 KB/s at 0% CPU and never completed**. With
exclusions it loads in ~182s. This is a required setup step on Windows, not a
tip. In an **Administrator** PowerShell:

```powershell
Add-MpPreference -ExclusionPath "<repo>\lean_project"
Add-MpPreference -ExclusionPath "$env:USERPROFILE\.elan"
Add-MpPreference -ExclusionPath "$env:USERPROFILE\.cache\mathlib"
Add-MpPreference -ExclusionPath "<python>\Lib\site-packages\lean_interact"
```

Linux needs none of this.

### 4. Verify the install

```bash
python tests/test_verifier.py
```

35 hand-labelled Lean snippets, prints a confusion matrix. Agreement should be
35/35.

## Mathlib load time and caching

`import Mathlib` dominates every other cost by orders of magnitude, so it is
paid once and reused three ways: a **build cache** so Mathlib is downloaded once
per machine, a **shared REPL environment** so it is imported once per process,
and an **environment snapshot** so later processes restore instead of importing.

| Stage | Cost | Paid |
|---|---|---|
| `lake exe cache get` (8,639 files) | multi-GB download | once per machine, into `~/.cache/mathlib` |
| Full setup from a clean clone, cache warm | **1574s** | once per clone |
| REPL up + Mathlib env, Defender exclusions in place | **359–645s** (env alone 134–162s) | once per process |
| One verification against the shared env | **0.12–0.53s** | per trace |

Measured on one Windows box, same Mathlib, same day:

| Clone | Defender exclusion | Cold (no snapshot) | Warm (snapshot exists) |
|---|---|---|---|
| main repo | yes | 389.5s (env 182.5s) | **359.2s** (env 134.1s) |
| clean clone | **no** | 978.1s (env 432.6s) | **920.8s** (env 394.6s) |

Two things follow, and the second one is easy to get backwards:

1. `lake exe cache get` on the clean clone reported **"No files to download"** — the
   shared build cache is what makes a second clone cheap, and it works.
2. **The Defender exclusion matters far more than the environment snapshot.** In an
   excluded path the snapshot is worth having; in an unexcluded one it saved only
   ~6% (978s → 921s), because the cost is Defender inspecting ~8,600 `.olean`
   files on read, which the snapshot does not avoid. Adding the exclusion is
   worth ~2.6x. Do not skip step 3 and expect the snapshot to compensate.

The snapshot path is `config.ENV_PICKLE_PATH`, created automatically on the first
run that imports Mathlib; the build cache honours `MATHLIB_CACHE_DIR` (default
`~/.cache/mathlib`). Deleting either only costs time, never correctness.

`config.VERIFY_TIMEOUT_SECONDS` is the **per-verification** budget and applies to
warm verifications, where the typical cost is well under a second. Building the
base environment has its own much larger budget (`BASE_ENV_TIMEOUT_SECONDS`) —
do not conflate them. A verification that exceeds its budget is recorded as the
outcome `timeout`, the REPL is restarted, and the run continues; it is never
silently folded into `invalid`.

## Usage

### Generate trajectories (GPU, no Lean)

```bash
python trace_valid.py generate --temp 0 --num-samples 50 --num-trajectories 1
```

Writes `traces/temp0.0_n50_1each/traces.jsonl` plus `run_meta.json`. A run
directory is named for its config, so a later temperature never overwrites an
earlier one, and an existing traces file is never overwritten — pass `--resume`
to continue it.

Sweep several temperatures in one process (the model is loaded once and reused;
loading a second copy would fail the VRAM preflight):

```bash
python trace_valid.py generate --temp 0 0.2 0.5 0.8 1.0 --seed 0 \
    --num-samples 50 --num-trajectories 1
```

Sampling (`--temp` > 0) without `--seed` is an error, because the run could not
be reproduced; `--allow-unseeded` records `seed=null` deliberately.

**Sample selection.** FormalStep is one row per CoT step, ordered by problem
(~62 steps each, 500 problems in train), so the first 50 rows are 50 steps of one
problem. Default `--sample-strategy distinct_problems` takes one step from each
of N different problems, striding across the problem list (`--stride`), choosing
the `first` or `median` step of each (`--step-selection`). `head` reproduces the
old single-problem behaviour. Selection is deterministic — no RNG.

Inspect prompts and selection without loading the model:

```bash
python trace_valid.py generate --dry-run --num-samples 50 --num-trajectories 1
```

**Run metadata.** Every run writes `run_meta.json` beside its traces: git
SHA/branch/dirty, model, temperature, top_p, seed, dataset name/split/
fingerprint, the full realised sample selection (rows, problem ids, level and
state counts), host/GPU/library versions, and the output record count, sha256
and elapsed time. It is written before the model loads and rewritten at the end
with `status: complete | incomplete`.

On a host that runs from an uploaded archive rather than a clone, `git` cannot
answer, so write a `CODE_VERSION` file next to the source at deploy time:

```bash
python -c "import json,subprocess as s; print(json.dumps({
  'sha': s.check_output(['git','rev-parse','HEAD']).decode().strip(),
  'branch': s.check_output(['git','rev-parse','--abbrev-ref','HEAD']).decode().strip(),
  'dirty': bool(s.check_output(['git','status','--porcelain']).decode().strip())}))" > CODE_VERSION
```

`run_meta.json` records which source answered under `git.source`.

### Verify traces in Lean (no GPU)

```bash
python verify_traces.py --traces traces/temp0.0_n50_1each/traces.jsonl \
    --out results/verify3_temp0.0.jsonl --all
```

Outcomes are `valid`, `compile_error`, `has_sorry`, `empty_code`,
`parse_failure`, `statement_error`, `statement_mismatch`, `unsound_axioms`,
`timeout`, `verifier_crash`. Only `valid` means a proved theorem; the rest are
distinct failures and are never collapsed into a boolean.

Three of those are not verdicts on the model's proof and never count as invalid:

- **`statement_error`** — Lean rejected the *goal*, so the proof was never
  judged. Confirmed per record by re-verifying the statement alone with `sorry`
  as its proof (`verifier.statement_is_broken()`), not by matching error text.
- **`statement_mismatch`** — something compiled, but it was not the dataset's
  statement, or the file declared more than one theorem. This is a pipeline
  alarm: if it is ever non-zero, fix generation before reading any rate.
- **`parse_failure`** — nothing usable reached Lean at all.

**`unsound_axioms` is a verdict, and a damning one.** The file compiled but the
theorem depends on an axiom outside `{propext, Classical.choice, Quot.sound}` —
most importantly one the generation declared itself. Checked by asking Lean
(`#print axioms`), so it also catches an axiom pulled in through a lemma.

### Which verification file is canonical

Three passes exist for the n50 runs and they are **not interchangeable**:

| file | verifier state | T=0.0 result |
|---|---|---|
| `results/verify_temp0.{0,2}.jsonl` | before the `maxRecDepth` and `statement_error` fixes | 36/50 — **superseded** |
| `results/verify2_temp0.{0,2}.jsonl` | after those two fixes | 37/50 |
| `results/verify3_temp0.{0,2}.jsonl` | **current** — adds the axiom audit, the statement-fidelity check and fail-closed classification | see `results/SUMMARY_n50_distinct.md` |

Always analyse the newest pass. `results/SUMMARY_n50_distinct.md` names the one
its numbers come from.

### Analyse

```bash
python analyze_runs.py results/verify3_temp0.0.jsonl results/verify3_temp0.2.jsonl \
    --out results/analysis.json
```

Prints the outcome distribution, the validity rate under both denominators, the
cross-tab of trace validity against the dataset's own provability label, and —
given two runs over the same samples — a paired comparison of which samples
changed outcome.

`timeout`, `verifier_crash` and `parse_failure` are *not* verdicts about a proof.
They are excluded from the validity rate's denominator, reported separately, and
the excluded count is always printed.

**On "answer correctness".** This pipeline cannot measure it. Goedel-Prover emits
a Lean proof, not a final answer, and FormalStep's `ground_truth` is the whole
problem's answer, identical for every step of that problem. The second axis in
the cross-tab is the dataset's `state` label — whether the *statement* is
provable — which is a different question from whether the model's proof
compiles. Do not relabel it "correctness".
